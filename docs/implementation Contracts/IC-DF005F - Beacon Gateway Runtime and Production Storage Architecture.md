# IC-DF005F — Beacon Gateway Runtime and Production Storage Architecture

## Outcome

DF005-F establishes provider-neutral Gateway runtime, transactional-storage, readiness, monitoring, and abuse-boundary contracts. It does not select, configure, deploy, or connect a production provider. Production remains `NOT_CONNECTED`.

## Hosting discovery

Hardware Radar's deployment artifact is the static `public/` tree generated by `npm run build:public`. Historical project records identify Cloudflare hosting and GitHub continuous deployment, but the repository has no `.github` workflow, Cloudflare Worker/Pages Function configuration, server package, database binding, or serverless deployment manifest. Cloudflare's static role does not authorize choosing Workers, D1, KV, Durable Objects, or another write technology.

## Runtime contract

The runtime capability assessment requires HTTPS, POST routing, pre-parse body limits, content-type inspection, response control, server-side secrets/configuration, storage access, concurrent-request safety, PII-safe operational logging, health diagnostics, and deployment independent of static assets. Missing capabilities prevent runtime readiness.

`BeaconGatewayTransportAdapter` passes sanitized requests to the certified governed handler. It may pass a transient client address only to the injected rate limiter. It never forwards transport context into Beacon, and reports only categorical accepted, duplicate, conflict, rejected, storage-failure, and rate-limited metrics plus latency. Raw requests and identities are not logged or exposed by health diagnostics.

## Production-storage contract

Production storage must provide durability, atomic compare-and-insert, unique event identity, concurrent writers, process independence, deterministic listing, constraint failure, backup/recovery, and retention/deletion capability. `TransactionalFirstPartyProductInterestCollectionRepository` consumes a provider adapter with atomic `compareAndInsert` and `listRecords` operations. Storage owns the race: concurrent exact events produce one accepted record plus duplicates; concurrent conflicting evidence allows only one material record and fails the other closed.

The DF005-E file adapter is explicitly assessed as non-production because its queue is single-process and it lacks storage-level uniqueness, multi-instance coordination, approved backup/recovery, and retention deletion. No database schema or vendor migration is created without an infrastructure decision.

## Atlas, retention, and activation

The required Atlas strategy is packaged/generated, read-only Atlas repositories in the server runtime. Gateway cannot mutate Atlas. Beacon remains authoritative for product and retailer resolution through those repositories.

No behavioral retention duration is approved. Retention remains a mandatory unresolved decision; production cannot advance to backend-ready status without it. The chosen store must support later governed deletion, but DF005-F neither expires nor deletes evidence.

No reusable runtime rate limiter or monitoring backend exists. Production requires infrastructure-level rate limiting (transient IP use permitted, never persisted) and privacy-safe categorical monitoring before deployment. Interest remains untrusted behavioral evidence, not unique-user demand, conversion, popularity, or ranking.

## Readiness states

- `NOT_CONNECTED`: no runtime/provider selected.
- `RUNTIME_SELECTED`: a runtime is named but one or more backend prerequisites remain incomplete.
- `BACKEND_READY_NOT_DEPLOYED`: runtime, transactional storage, retention, rate limiting, monitoring, Atlas read model, and deployment configuration are ready, but deployment has not occurred.
- `DEPLOYED_NOT_BROWSER_CONNECTED`: backend deployed; public browser still disconnected.
- `CONNECTED`: reserved for a later increment after separately approved browser wiring.

Current state is `NOT_CONNECTED`. The read-only collection-status command exposes requirements and readiness without records, secrets, or mutation.

## Isolation

DF005-F adds no public `fetch()` or click listener, no deployment, no storage credentials, no production signal, and no third-party analytics import. Gateway/Beacon has no write dependency on Mercury. Cadence, E2O/E2N, automatic execution, unattended LIVE, acquisition, evidence, history, canonical observations, publication, and spend remain unchanged.
